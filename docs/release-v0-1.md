# Standard de sortie V0.1

## Objectif
Une V0.1 doit démontrer un premier cas d'usage réel ou réaliste, sans prétendre résoudre tout le problème.

## Gate 1 — Problem
- [ ] problème documenté
- [ ] utilisateurs identifiés
- [ ] hypothèses explicites
- [ ] expert métier identifié lorsque nécessaire

## Gate 2 — Product
- [ ] parcours principal défini
- [ ] MVP limité
- [ ] critères d'acceptation écrits

## Gate 3 — Engineering
- [ ] architecture documentée
- [ ] installation reproductible
- [ ] tests critiques
- [ ] erreurs principales gérées
- [ ] logs/observabilité minimaux

## Gate 4 — Risk
- [ ] threat model ou risk review
- [ ] données sensibles identifiées
- [ ] permissions contrôlées
- [ ] limites documentées
- [ ] revue spécialisée pour les domaines à risque

## Gate 5 — Validation
- [ ] scénarios de validation exécutés
- [ ] résultats documentés
- [ ] baseline disponible
- [ ] KPI défini
- [ ] décision de pilote documentée

## Gate 6 — Release
- [ ] README à jour
- [ ] changelog à jour
- [ ] version taguée
- [ ] known limitations publiées
- [ ] issue de release clôturée après vérification

## Règle
Pas de pilote uniquement parce que le logiciel fonctionne. Le pilote doit être justifié par la préparation du produit, du risque, du terrain et de la mesure d'impact.
